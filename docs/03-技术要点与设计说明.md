本文说明每项技术要点「解决什么问题 / 怎么实现 / 代码在哪 / 怎么验证」。

## 一、稳定性八项机制

### 1. 双层限流
- **网关层**：`KVStore.sliding_window_allow()` 滑动窗口（内存实现用时间戳集合，Redis 实现用 ZSET + Lua 脚本保证原子性）。单用户每分钟 10 次、全局 200 QPS；超限抛 `RateLimitError` → 429 + `Retry-After` 头。
- **服务层**：`LLMConcurrencyLimiter`（`asyncio.Semaphore`）把大模型并发压到 20 以内。
- **为什么双层**：网关挡恶意刷量，服务层挡正常用户的并发洪峰。
- 代码：`common/kvstore.py`、`common/ratelimit.py`、`gateway/middleware.py`
- 验证：`tests/test_stability.py::test_sliding_window_rate_limit`

### 2. 熔断与降级
- 每个下游（每个模型、每个工具）独立一个 `CircuitBreaker`：10 秒窗口，失败率 ≥ 50% 且样本数 ≥ 5 打开；30 秒冷却后进入半开，放行探测，全成关闭、失败重开。
- **降级分层**：大模型不可用 → 规则引擎生成参考行程并标注「降级模式」；工具不可用 → 该工具返回兜底 stub，不阻塞主流程。
- 代码：`common/circuit_breaker.py`、`common/resilience.py`、`services/agent_service/service.py::_degraded_draft`
- 验证：`test_circuit_breaker_opens_and_recovers`、`test_agent.py::test_degrade_when_model_down`

### 3. 有限重试
- 只重试瞬时错误（超时 / 429 / 5xx）；业务错误（校验失败）永不重试。指数退避 + ±20% 抖动，单请求最多 2 次。
- 代码：`common/resilience.py::call_with_resilience`
- 验证：`test_retry_then_success`、`test_business_error_not_retried`

### 4. 幂等
- 前端为每次规划生成 `request_id`(UUID)；后端 `SETNX` 占位，TTL 10 分钟。已完成返回缓存结果，进行中返回「处理中」。大模型绝不被同一请求调用两次。
- 代码：`common/idempotency.py`
- 验证：`test_idempotency_flow`、`test_agent.py::test_idempotent_replay`

### 5. 分布式锁
- `SET lock:plan:{user_id}` NX EX 60；看门狗每 20 秒续期；释放用 Lua 比对 value 防误删。未抢到锁 → 「已有规划任务进行中」。
- 代码：`common/distlock.py`
- 验证：`test_distributed_lock_exclusive`

### 6. SSE 生命周期管理
- 连接管理器维护 `conn_id → (user_id, asyncio.Task)` 注册表，在线连接数作为监控指标。每 15 秒 ping 心跳；断开清理链：取消规划任务 → 关闭 LLM 流 → 写回会话状态 → 释放锁。
- 代码：`services/agent_service/sse/manager.py`、`service.py::chat_event_stream`
- 验证：`/api/admin/sse` 查在线连接；SSE 流中可见 `ping`。

### 7. Prompt 防护
- 输入侧正则拦截注入话术 + 长度限制 2000；角色隔离（用户文本仅作为 user 消息、加「【用户旅行需求】」前缀）；输出侧审计偏离规划的请求。
- 代码：`services/agent_service/guard/prompt_guard.py`
- 验证：`tests/test_api.py::test_prompt_injection_blocked`（400/40001）

### 8. Token 用量管控
- 按用户每日配额（默认 10 万），调用前查计数，超额拒绝；调用台账 `llm_call_logs` 记录 model/tokens/latency/trace_id。
- 代码：`common/quota.py`、`services/agent_service/service.py::_log_llm_call`
- 验证：`tests/test_api.py::test_usage_endpoint`

## 二、Agent 关键设计

### Function Calling 主线
- 工具以 JSON Schema 注册（`tool_service/tools.py::TOOL_SCHEMAS`），随请求传给模型 `tools` 参数；模型返回 `tool_calls` 后由服务端执行并回喂结果，形成 ReAct 式循环（`core/nodes.py::tool_call`）。参数经白名单二次校验，未知工具不执行。

### Reflection 自检 + 修订封顶
- `reflect` 节点三维度自检：预算是否超支、同日景点是否重复、单日时长是否过满。
- 超预算且 `revision_count < 3` 时降档（住宿档位、过滤高票价景点）后回到 `plan` 重装配；否则输出当前草稿并提示。
- 代码：`core/nodes.py::reflect`、`assemble_draft`

### 分层记忆
- 短期：会话状态存 KV，TTL 2 小时；上下文用「最近 N 轮原文 + 更早摘要」滑动窗口。
- 长期：从消息抽取稳定偏好（如「不想爬山」）回写 `user_preferences`，后续规划自动生效。
- 代码：`memory/short_term.py`、`memory/long_term.py`

## 三、RAG 设计

- **切片**：先按句子结构切，再限长（默认 380 字符）+ 相邻重叠（50 字符）；每块附 `city/title/doc_id` 元数据。
- **Embedding**：默认本地确定性哈希向量（中文字 + 双字词组特征哈希，投影 256 维并归一化）；配 Key 后可选真实 Embedding。查询与语料同一编码，保证同空间可比。
- **检索**：两级过滤——先按城市元数据过滤，再按余弦阈值剔除；top-k=5，阈值无命中时放宽阈值兜底（仍按城市过滤）。
- **注入**：拼成「参考资料」并保留块编号，前端展示引用来源；明确允许模型说「不知道」。
- **为什么需要（与 Function Calling 互补）**：实时结构化事实走工具；静态非结构化知识（开放时间、政策、避坑）无 API 可查，走 RAG。
- **为什么用内存向量库而非 pgvector**：环境约束下需零依赖可运行；接口与 pgvector/HNSW 方案对齐，生产替换 `rag/store.py` 即可。
- 代码：`services/agent_service/rag/{chunker,embeddings,store,retriever}.py`
- 验证：`tests/test_rag.py`

## 四、数据层设计

### 表结构（三级行程）
`trips`（目的地/天数/预算/状态/version）→ `trip_days`（day_no/city/weather_snapshot）→ `itinerary_items`（seq/time_slot/poi_name/category/cost/duration_min）。
另有 `users`、`user_preferences`（长期记忆回写）、`agent_sessions`（会话状态）、`llm_call_logs`（调用台账）。
拆分收益：单天操作不动全表，前端可按需加载。行程项冗余 `poi_name`（反范式）以列表免连表。

### 索引
- `trips`：`idx_trips_user_updated(user_id, updated_at)` 支撑列表排序
- `trip_days`：`uk(trip_id, day_no)` 唯一约束
- `itinerary_items`：`idx_items_day_seq(day_id, seq)` 顺序读取
- `llm_call_logs`：`(user_id, created_at)` 成本统计、`(trace_id)` 链路排查

### 事务与一致性
- 行程保存为强一致场景，三级同事务写入；更新用「先删后插」全量替换（Agent 每次产出完整行程）。
- 并发修改由 `trips.version` 乐观锁兜底，版本不匹配 → 40901 提示刷新。
- 缓存采用 cache-aside（读缓存未命中回填并设 TTL）。

### 缓存键（Redis 形态）
| 对象 | 键 | TTL |
|---|---|---|
| 会话状态 | `session:{session_id}` | 2 小时 |
| 幂等键 | `idem:{request_id}` | 10 分钟 |
| 规划锁 | `lock:plan:{user_id}` | 60 秒可续期 |
| 限流窗口 | `rl:user:{user_id}` / `rl:global` | 60s / 1s |
| Token 配额 | `quota:tokens:{user_id}:{date}` | 2 天 |

## 五、可观测性

- **结构化日志**：JSON 输出，每条携带 `trace_id / user_id / session_id`，见 `common/logging.py`。
- **链路追踪**：轻量 Span 记录器（对齐 OpenTelemetry 语义），贯穿「网关 → agent.run → node → 工具/模型」，`/api/admin/traces` 可按 trace_id 查看。生产替换为 OTel SDK + Jaeger。
- **指标**：`/api/admin/overview` 与 `/api/admin/metrics`（Prometheus 文本）覆盖 QPS、P95 时延、token/小时、熔断器状态、SSE 在线连接数。
- **故障演练**：`/api/admin/fault` 可动态注入模型/工具故障，观察熔断与降级（答辩可现场演示）。

## 六、接口约定

- 全部 RESTful，统一响应 `{code, message, data}`；错误码五位数字，前三位对应 HTTP 语义，后两位为业务子码（`42901` 限流、`42902` 配额、`50301` 模型降级、`40901` 乐观锁冲突）。
- `/api/agent/chat` 是全系统唯一 SSE 接口；响应头返回 `X-Trace-Id`，用户报障凭此在 `/api/admin/traces?trace_id=` 拉出完整链路。
