# 功能扩展说明（旅行吧 · 管理后台 · 真实工具 · 模型选择）

在原有「对话式行程规划」基础上，本轮新增了社交动态社区、双角色管理后台、
真实第三方数据工具与模型选择能力。以下说明设计、接口与实现位置。

---

## 一、角色与权限（管理员 / 用户）

| 角色 | 能力 |
|---|---|
| `user` | 发布/编辑/删除**自己的**动态、点赞/收藏/留言、规划行程、管理自己的行程、个人设置 |
| `admin` | 上述全部 + **内容审核**（下架/通过/删除任意动态）+ **系统设置**（大模型、向量模型、知识库参数）+ **知识库管理** + 概览看板 |

- 用户表新增 `role`（默认 `user`）、`bio` 字段；`UserOut` 返回 `role` 供前端决定是否显示「管理」栏目。
- 后端以 `require_admin` 依赖统一鉴权，普通用户访问 `/api/admin/**` 返回 **403（40301）**。
- 演示账号：普通用户 `demo / demo123`；管理员 `admin / admin123`。

---

## 二、旅行吧（社交动态）

**像 QQ 动态一样的信息流**：图文帖子、点赞、收藏、留言、城市筛选、按最新/最热排序、帖子详情、发布与编辑。

- 数据模型：`posts`（标题/正文/城市/地点/图片 JSON/标签 JSON/计数/状态/作者）、`comments`、`post_likes`（唯一约束）、`post_collects`（唯一约束）。
- 索引：`(status, created_at)` 支撑动态流，`(city)` 支撑城市筛选，`(user_id)` 支撑我的动态。
- 帖子状态：`published` / `pending` / `rejected`，供管理员审核。
- 图片使用 `text_to_image` 生成的真实风光图（`backend/app/db/seed.py` 中 `_img()`），共 **14 条种子动态**、多作者、含评论与点赞。
- 接口：`GET /api/posts`、`GET /api/posts/{id}`、`POST/PUT/DELETE /api/posts`、
  `POST /api/posts/{id}/like | /collect | /comments`、`GET /api/posts/cities`、`GET /api/posts/mine/collections`。
- 实现位置：`backend/app/services/feed_service/router.py`、`backend/app/schemas/feed.py`。

## 三、真实数据与工具

「网站必须有真实的信息」落地为**真实数据源 + 明确的降级策略**。

| 工具 | 真实来源 | 说明 |
|---|---|---|
| `get_weather` | **Open-Meteo**（`api.open-meteo.com`，无需 Key） | 真实实时预报：天气码、最高/最低温、降水概率；失败回落确定性 mock |
| `plan_route` | **OSRM**（`router.project-osrm.org`，无需 Key） | 城市间真实驾车距离与时长（实测 成都→西安 726km / 498min）；市内两景点回落规则估算 |
| `geocode` | 内置真实城市坐标表（WGS84，38 座城市） | 地图定位；生产可换高德/OSM Nominatim |
| `search_poi` | 精选景点数据集（真实景点名/票价/开放时间）+ 真实城市中心坐标 | 每景点附确定性偏移坐标用于地图打点 |
| `estimate_budget` | 本地规则引擎 | 门票/住宿/餐饮/交通拆分 |

- 返回体统一带 `source` 字段（`open-meteo` / `osrm` / `local-city-table` / `curated-dataset` / `mock`），便于辨识数据来源。
- 网络调用放在线程池（`asyncio.to_thread`）避免阻塞事件循环，并受统一的超时/重试/熔断链路保护。
- 地图在前端用 **Leaflet + OpenStreetMap 瓦片**（无需 Key）渲染真实地理位置；规划草稿的 `day_list[].items[]` 现带 `lat/lon`，`plan_update` 含 `center`。
- 实现位置：`backend/app/services/tool_service/{providers,geo,tools}.py`。

## 四、大模型真实有效与模型选择

- 统一适配器 `LLMAdapter.chat(messages, tools, model)`；`provider / base_url / api_key / default_model / temperature / max_tokens` 全部来自**运行时配置**（`system_settings` 表，管理员可改，即时生效，无需重启）。
- **模型选择器**位于规划页输入框左侧（仿 Trae），数据来自 `GET /api/agent/models`；`POST /api/agent/chat` 接受 `model` 字段并透传至适配器。
- 未配置 API Key 时自动回落为**离线模拟**输出（保证演示与测试），配置 Key 后即调用真实模型。
- 每次调用写 `llm_call_logs` 台账（模型名、tokens、耗时、trace_id），支撑成本统计。
- 实现位置：`backend/app/common/runtime_config.py`、`backend/app/services/agent_service/llm/adapter.py`。

### 用户级模型配置（只需填密钥）
- 模型为**固定配置**，仅两个：`deepseek-v4-flash`（DeepSeek V4 Flash）与 `deepseek-4.1-flash`（DeepSeek 4.1 Flash）；
  Base URL / 温度 / max_tokens 等**固定项不对用户下发**，用户只需填写自己的 **API Key**。
- 接口：`GET/PUT /api/users/model-config`（密钥只回传「是否已配置」布尔值，`clear_api_key=true` 可清除）。
- 规划请求优先使用用户自己的 Key，其次管理员全局 Key，两者都没有则用离线模拟。
- 前端：个人中心的「模型配置」区块仅展示两个模型 + API Key 输入框（+ 保存/清除），区块顺序为
  「头像与资料 → 模型配置 → Token 用量 → 偏好管理 → 我的收藏 → 我的评论 → 历史会话」。

### 「配置了真实密钥却用不了模型」的根因与修复
这是一次真实排障，根因有三层，均已修复：

| # | 根因 | 修复 |
|---|---|---|
| 1 | 展示用模型名 `deepseek-v4-flash` / `deepseek-4.1-flash` **不是 DeepSeek 官方 API 的模型 ID**，上游返回「Model Not Exist（400）」 | 模型目录新增 `api_model` 与 `fallbacks`：把展示 id 解析成**真实上游模型名尝试链**（如 `deepseek-v4-flash → deepseek-chat`），自动匹配账号实际可用的模型并**记住结果**（`_WORKING_MODEL` 缓存），下次直接用对的 |
| 2 | `resp.raise_for_status()` 抛出的 `httpx.HTTPStatusError` 被当作**普通异常不重试**，且错误信息不可读 | 把上游错误翻译成**可读中文**（401 密钥无效 / 402 余额不足 / 403 无权限 / 429 限流 / 5xx 上游异常 / 模型不存在）；429、5xx、超时转为可重试的瞬态错误走韧性链路 |
| 3 | agent 的 `except Exception` **静默降级**成参考模板，用户只看到「智能规划暂时不可用」，完全不知道是密钥问题 | 新增 `LLMUpstreamError` 分支：把真实原因通过 SSE `error` 事件（`code:50201, fatal:false, fallback:true`）与对话文本如实告知用户，再给出参考行程 |

另外新增 **连通性自检** `POST /api/users/model-config/test`：用当前（或刚填入的）密钥真实发一次最小请求，
返回 `{ok, message, model_used}`；`ok=false` 时 `message` 即为可读的上游错误 —— 用户不用再靠猜。

> 实测：填入无效密钥后，自检返回「API Key 无效或已失效（401），请在个人中心重新填写正确的 DeepSeek 密钥。」，
> 对话流中同样出现该提示并附带降级说明，不再静默失败。

## 六之前：图片保存到后端图片文件夹 + 个人信息存 MySQL（media-service）

风景配图、用户头像等图片**文件本体保存在网站后端的图片文件夹** `backend/static/uploads/`（按 kind 分桶、sha256 前缀二级目录），
数据库（生产为 MySQL）只登记元数据与相对路径；由后端 `GET /api/media/{id}`（FileResponse）统一提供，不再依赖外部图床（避免离线/被墙导致整屏空白）。

- 表结构：`media(id, owner_id, kind, filename, mime, size, sha256, path, source_url, created_at)`；
  `sha256` 唯一去重（同一张图重复上传只落盘一份），`(owner_id, created_at)` 建索引；`path` 为相对 uploads 根的路径。
- 接口：
  - `POST /api/media/upload?kind=image|avatar`（multipart，≤5MB，jpeg/png/webp/gif）→ `{id, url, size, mime}`
  - `GET /api/media/{id}` → FileResponse 直接返回磁盘图片（`Cache-Control: immutable`）
  - `GET /api/media/mine/list` → 我的图片
  - `POST /api/admin/media/sync`（管理员）→ 把历史外链图片下载落盘并替换地址
  - `GET /api/admin/media/stats`（管理员）→ `{count, bytes, mb}`
- **首次启动自动迁移**：`auto_migrate_once()` 在媒体表为空时后台执行，把种子动态的外链配图下载落盘，
  不阻塞启动；下载失败的条目保留原地址，不影响业务。
- 个人信息（昵称/简介/头像地址/角色）保存在 **MySQL `users` 表**，头像引用 `media` 表登记的本地图片。
- 实测结果：14 条种子动态的 **17 张配图全部本地化**（去重后 16 个文件落盘 static/uploads，约 4.04 MB），帖子图片地址 **0 条外链残留**。

## 五、RAG 真实存在与知识库可配置

- 语料来源改为**数据库 `kb_documents`**（启动时由内置 `data/knowledge_base.json` 初始化），管理员可增删改，并**重建索引**（`POST /api/admin/kb/reindex`）。
- 切片参数、top-k、相似度阈值、Embedding 提供方均来自**运行时配置**，管理员在「系统设置 → 向量与知识库」调整后**自动重建索引**。
- **检索测试**接口 `POST /api/admin/kb/search?query=&city=` 返回命中的块与相似度分数，用于证明 RAG 真实可用（我在冒烟测试中实测命中新建知识条目）。
- 检索链路：结构切片 → 定长（默认 380 字）+ 重叠（50 字）→ 归一化向量 → 城市元数据过滤 → 余弦 top-k → 阈值剔除；结果注入 Prompt 并回传引用来源（citations）。
- 实现位置：`backend/app/services/agent_service/rag/*`、`backend/app/services/admin_service/router.py`。

## 六、前端结构（仿 Trae 单列导航）

左侧**可折叠**单列导航（展开 ~232px / 收起 ~64px 仅图标，状态持久化）：

| 栏目 | 路由 | 说明 |
|---|---|---|
| 旅行吧 | `/feed`、`/feed/:id` | **登录后默认页**，风光动态流 + 点赞/收藏/留言 + 详情 + 发帖 |
| 新建规划 | `/plan` | 智能体对话，输入框左侧模型选择器，右侧行程预览 + 真实地图，可「保存为行程」 |
| 个人行程 | `/trips`、`/trips/:id` | 行程增删改查与管理 |
| 管理 | `/admin` | 仅管理员可见：内容审核、大模型/向量/知识库设置、知识库管理、概览 |
| 个人中心 | `/profile` | 头像与资料、模型配置（仅需 API Key）、Token 用量、偏好、我的收藏、**我的评论**、历史会话 |

右上角头像与设置入口保持不变，并新增「我的收藏」；默认头像为昵称首字母，可在个人中心自定义（上传/URL/预设）。
