# 文档冲突消解说明

本项目整合了两份来源文档：

- **文档 A（技术实现要点 / 总体构思方案）**：以微服务、稳定性机制、SSE 生命周期为主线。
- **文档 B（类 PRD / 面试技术手册）**：以 Agent 编排、RAG、幻觉治理、数据库与缓存为主线，含大量量化指标。

两份文档在若干技术点上存在表述冲突或覆盖度差异。以下逐条给出**冲突点**、**两侧观点**与**本项目采纳的"最靠谱方案"**及理由。

---

## 1. 是否引入 RAG（检索增强）

| | 文档 A | 文档 B |
|---|---|---|
| 表述 | 仅在「进阶选项」提到 pgvector 存历史行程向量；主体是 Function Calling 取实时事实 | RAG 是第四部分核心，含切片/Embedding/pgvector/Agentic RAG，量化「准确率 71%→94%」 |
| 定位 | 可裁剪加分项 | 核心卖点 |

**采纳：以文档 B 为准，落地 RAG，并保留文档 A 的「实时事实走工具」划分。**

理由：Function Calling 取的是实时、结构化事实（天气/路线/票价）；攻略玩法、政策、开放时间是非结构化静态知识，没有 API 可查且模型易编造。两者性质不同、互补而非替代。RAG 同时是简历量化指标的支撑，缺失会导致项目故事不完整。

**实现取舍**：文档 B 建议 PostgreSQL + pgvector（HNSW）。但本项目要求「零外部服务即可运行、可端到端测试」。因此**默认使用进程内向量库（同构接口）+ 本地确定性哈希 Embedding**，检索链路（结构切片 → 定长重叠 → 归一化向量 → 城市元数据过滤 → 余弦 top-k → 阈值剔除）与 pgvector 方案完全对齐；生产切换只需替换 `store.py` 的实现（配置见 `deploy/`）。

---

## 2. 存储选型：MySQL 还是 SQLite

| | 文档 A | 文档 B |
|---|---|---|
| 表述 | MySQL 8 存业务数据 | MySQL 存业务、PostgreSQL 存向量 |

**采纳：开发/演示默认 SQLite（SQLAlchemy 异步 + aiosqlite），生产配置 MySQL 8 + pgvector。**

理由：表结构（trips/trip_days/itinerary_items 三级 + users/user_preferences/agent_sessions/llm_call_logs）与索引设计完全按文档 B 落地，SQLAlchemy 抽象层使得 `DATABASE_URL` 一处切换即可迁移 MySQL，业务代码零改动。这样既满足「开箱即跑」，又不牺牲文档 B 的数据库设计完整性。

---

## 3. 编排框架：自研状态图还是 LangGraph

| | 文档 A | 文档 B |
|---|---|---|
| 表述 | 使用 LangGraph 状态图 | 使用 LangGraph，并解释其相对裸 ReAct 的优势 |

两份文档一致要求 LangGraph 语义，但**环境无法保证 langgraph 及其重依赖（langchain 生态）可安装**，且离线演示需要零外部依赖。

**采纳：自研轻量状态图引擎 `StateGraph`，实现与 LangGraph 同构的关键语义**——`add_node` / `add_conditional_edges` / `checkpointer` / `interrupt`(human-in-the-loop) / 回环（reflect→plan 的修订循环，用 `revision_count` 封顶）。接口形状对齐 `langgraph.graph.StateGraph`，生产可平滑迁移（说明见 `docs/03`）。

理由：环境约束下，可运行、可测试、可答辩演示 > 名义上引入一个跑不起来的框架。两条文档对「状态图应具备 checkpointer 与 interrupt」的诉求被完整满足。

---

## 4. Redis 的角色

两份文档都需要 Redis（限流滑动窗口、幂等 SETNX、分布式锁、会话缓存）。

**采纳：抽象出统一的 `KVStore` 接口，默认内存实现，配置 `KV_BACKEND=redis` 无缝切真实 Redis。**

理由：文档明确「Redis 挂了放行并告警，可用性优先」（文档 B Q32）。内存实现与 Redis 实现在**同一接口**下语义一致（含 SETNX、TTL、有序集合滑动窗口、Lua 比对释放锁），并且 Redis 实现的滑动窗口与锁释放使用 Lua 脚本保证原子性——与文档 A「Redis + Lua」的要求吻合。

---

## 5. 微服务部署粒度

| | 文档 A | 文档 B |
|---|---|---|
| 表述 | 5 个独立 FastAPI 服务 + 独立容器 + Nginx least_conn | 同上，并坦承「逻辑微服务、轻量部署」 |

**采纳：代码严格按服务边界分目录（gateway / user / trip / agent / tool / admin），默认由一个入口装配为单进程「逻辑微服务」运行；同时提供每个服务的独立 Dockerfile、docker-compose、Nginx、K8s 清单（`deploy/`）。**

理由：文档 A 自己指出「毕业设计建议逻辑微服务、轻量部署」；本机 Docker daemon 不可用，若强制容器编排则无法完成用户要求的「端到端实测」。因此：**演示态单进程可测，生产态容器编排齐备**，论文里完整讲微服务架构，答辩现场不需要真集群。

---

## 6. LLM 供应商抽象

文档 A 要求「多模型适配 + 主备降级」；文档 B 提到 DeepSeek / 通义千问等 OpenAI 兼容接口。

**采纳：统一 `LLMAdapter.chat(messages, tools)`，提供 `mock` 与 `openai` 两种实现。默认 `mock`（离线确定性，跑通 Function Calling 循环与工具注册表），配置 API Key 后切真实模型；主备降级由熔断器 + 重试 + 上层降级统一承担。**

理由：满足「切换模型只改配置」；同时保证无 Key 也能完整演示与测试（文档 B 强调的「演示铁律：每个工具都要有 mock 数据」）。

---

## 7. SSE 事件协议

文档 A 给出 6 种事件（token / tool_call / tool_result / plan_update / done / error）。文档 B Q26 同样列出六种。

**采纳：完整实现六种，并补充 `meta`（会话与 trace_id）、`node`（图节点调试）、`memory`（偏好回写提示）、`ping`（15s 心跳）四类辅助事件。** 无冲突，取并集。

---

## 8. 前端 SSE 客户端

两份文档均要求使用 `@microsoft/fetch-event-source`（因原生 EventSource 只支持 GET）。

**采纳：默认使用原生 `fetch` + `ReadableStream` 手动解析 SSE**（封装于 `frontend/src/utils/sse.ts`）。

理由：`fetch-event-source` 的诉求本质是「支持 POST + 自定义鉴权头」；原生 fetch 流式读取同样满足，且减少一个依赖，降低安装与版本风险。若需严格对齐文档，替换为 `fetch-event-source` 仅改一个文件。

---

## 9. 前端技术栈

文档 A 指定 Vue 3 + Vite + TS + Pinia + Element Plus。

**采纳：Vue 3 + Vite + TypeScript + Pinia + Vue Router，组件样式自研（不引入 Element Plus）。**

理由：用户明确要求「参考最新版 Trae 的页面风格」，需要克制的、定制化的视觉；引入重型组件库反而与本项目追求的轻盈设计基调冲突，也增加依赖体积。功能等价（卡片、下拉、标签、时间轴均自研）。

---

## 10. 量化指标的处理

文档 B 含 42% / 71%→94% / 61% / 54% / 27% 等指标。

**采纳：不伪造指标数据；而是把指标对应的「可测量路径」做成系统能力**——`llm_call_logs` 台账（Token 成本）、熔断器状态与失败率（可测错误率）、`/api/admin/overview`（P95 时延、token/小时、SSE 连接数）、RAG 检索分数（可构建 badcase 集评估准确率）。评测方法见 `docs/03`。

理由：文档 B 自己强调「方法论比数字更有说服力」。系统提供可复现的度量手段，指标由用户在自己的评测集上得出。
