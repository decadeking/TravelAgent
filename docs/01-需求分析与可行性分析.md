# 需求分析与可行性分析

> 项目：基于 FastAPI 与 Vue 3 的交互式旅行规划智能体 TravelAgent
> 定位：对话式 AI 应用 + 微服务稳定性工程（毕业设计 / 求职作品）

---

## 一、项目背景与目标

传统旅行规划依赖人工在多个平台之间检索、比对、拼装，耗时且难以兼顾预算、偏好与时间约束。本项目以 **Agent 为核心**：用户用自然语言提出需求（「我要去成都玩 4 天，预算 3000 元，带小孩，不想爬山」），系统流式呈现规划过程，产出按天编排、可编辑、可保存的行程。

**三层价值**（决定评价维度）：

| 层次 | 内容 | 决定 |
|---|---|---|
| 表层 | 完整 Web 应用：注册登录、行程管理、偏好设置（标准 CRUD） | 项目是否完整可跑 |
| 核心层 | 会思考、能行动的智能体：状态图编排、Function Calling、RAG、分层记忆 | 论文/作品的深度 |
| 加分层 | 工程稳定性：限流、熔断、幂等、分布式锁、链路追踪、Token 管控 | 与「玩具 Demo」的区分度 |

## 二、需求分析

### 2.1 功能性需求（FR）

| 编号 | 需求 | 说明 | 优先级 |
|---|---|---|---|
| FR1 | 用户注册 / 登录 / 鉴权 | JWT(HS256)，bcrypt 存密码，网关统一校验并注入 user_id | 必做 |
| FR2 | 行程 CRUD | 行程→天→行程项三级结构；乐观锁防并发覆盖；按用户隔离防越权 | 必做 |
| FR3 | 对话式规划 | 自然语言输入 → 槽位抽取 → 缺失反问 → 生成行程 | 必做 |
| FR4 | Function Calling 工具调用 | 天气 / 景点 / 路线 / 预算 / 搜索，至少 3 个真实能力 + 全量 mock | 必做 |
| FR5 | SSE 流式输出 | 打字机效果 + 工具调用过程可视化 + 行程增量刷新 | 必做 |
| FR6 | RAG 知识检索 | 攻略/政策/开放时间等静态知识，切片检索注入 Prompt，标注引用 | 加分 |
| FR7 | 分层记忆 | 短期：会话状态 TTL；长期：稳定偏好回写并注入后续规划 | 加分 |
| FR8 | human-in-the-loop | 多轮修订（「第二天换个便宜点的」），断线可恢复会话 | 加分 |
| FR9 | 可观测性 | 结构化日志 + 链路追踪 + 指标看板 + 熔断状态 | 加分 |
| FR10 | 故障演练 | 一键注入模型/工具故障，观察熔断与降级 | 加分 |

### 2.2 非功能性需求（NFR）

| 编号 | 需求 | 目标 |
|---|---|---|
| NFR1 | 稳定性 | 下游（大模型/第三方）故障时系统降级而非雪崩；单请求失败可恢复 |
| NFR2 | 性能 | 会话恢复接口 P95 < 2s；列表查询走索引 |
| NFR3 | 安全 | 防越权（数据按 user_id 过滤）、Prompt 注入防护、密码哈希、输入限长 |
| NFR4 | 成本可控 | Token 按用户每日配额 + 模型分级 + 上下文压缩 + 调用台账 |
| NFR5 | 可运维 | 日志可检索、链路可追踪、指标可采集、故障可演练 |
| NFR6 | 可移植 | 默认零外部依赖可运行；生产可切 MySQL/Redis/pgvector |
| NFR7 | 可测试 | 核心机制与接口有自动化测试覆盖 |

### 2.3 核心用户流程

1. 注册登录，填写旅行偏好（预算档位、忌强度徒步、偏好人文/自然等）
2. 对话页自然语言提出需求
3. Agent 抽取槽位，缺失则反问；随后调用工具获取事实
4. SSE 流式输出规划过程，右侧预览区实时更新行程与地图点位
5. 用户确认或对话修改，Agent 局部更新行程（human-in-the-loop）
6. 保存行程，查看分日详情与预算拆分

## 三、可行性分析

### 3.1 技术可行性

| 关注点 | 结论 | 依据 |
|---|---|---|
| Agent 编排 | 可行 | 自研 `StateGraph` 实现 LangGraph 同构语义（节点/条件边/checkpointer/interrupt），不依赖重框架 |
| 大模型调用 | 可行 | 统一 `LLMAdapter`，`mock`（离线确定性）与 `openai` 兼容（DeepSeek/通义）双实现 |
| 流式输出 | 可行 | FastAPI `StreamingResponse` + 异步生成器，六类 SSE 事件 + 心跳 + 断开取消 |
| RAG | 可行 | 结构切片 + 定长重叠 + 归一化向量 + 城市元数据过滤 + 余弦 top-k，接口对齐 pgvector |
| 稳定性机制 | 可行 | 限流/熔断/重试/幂等/分布式锁均在统一 `KVStore` 上实现，内存与 Redis 双后端 |
| 数据层 | 可行 | SQLAlchemy 异步，默认 SQLite，`DATABASE_URL` 一处切换 MySQL |
| 部署 | 可行 | 开发态单进程逻辑微服务；生产态 Docker Compose 编排（配置齐备） |

### 3.2 经济可行性

- 默认 `mock` 模式 **零 API 成本**即可完成演示、答辩与自动化测试。
- 接入真实模型时：模型分级（简单任务小模型、规划大模型）+ 上下文压缩 + 每日配额，成本可显著下降（架构已支持，指标由 `llm_call_logs` 台账度量）。
- 基础设施：默认无需云资源；生产用单机容器编排即可。

### 3.3 时间可行性

分五阶段：筑基（CRUD 骨架）→ 智能化（模型/工具/SSE）→ 编排（状态图/记忆）→ 稳定性（限流熔断幂等锁）→ 打磨（测试/文档/演示）。本项目已一次性完成五阶段的可运行实现。

### 3.4 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 演示现场无网/第三方 API 抖动 | 展示中断 | 所有工具与 LLM 均有离线 mock（「演示铁律」） |
| 大模型慢/贵/不可靠 | 拖垮服务、成本失控 | 熔断 + 降级 + 有限重试 + 并发信号量 + Token 配额 |
| 用户断开后仍消耗 Token | 成本浪费 | SSE 连接注册表 + 断开即取消任务 |
| 并发重复请求 | 重复计费、数据覆盖 | 幂等键 + 分布式锁 + 乐观锁三层兜底 |
| 环境差异（Docker 不可用） | 无法实测 | 默认 SQLite + 内存 KV，零外部服务可跑 |
| 模型幻觉 | 信息错误 | RAG 提供依据 + 工具实时校验 + 自检 + 明确允许「不知道」 |

## 四、范围界定

| 档位 | 内容 |
|---|---|
| **必做（已实现）** | 用户与鉴权、行程 CRUD、单 Agent 对话规划、Function Calling ≥3 工具、SSE 流式、基础限流与重试 |
| **加分（已实现）** | 状态图编排、熔断降级、幂等、分布式锁、链路追踪、长期偏好记忆、human-in-the-loop、RAG、可观测性、故障演练 |
| **可裁剪/展望（文档说明）** | 多 Agent 协作、Agentic RAG（把 `search_kb` 封装为工具自主调用）、K8s 多集群 HPA 弹性伸缩 |

> 裁剪原则：每个写进论文的特性，都要有可演示路径。
