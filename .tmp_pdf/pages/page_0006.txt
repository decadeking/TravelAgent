Q8｜状态图怎么设计的？有哪些状态和节点
核心答案 状态五组字段：messages 对话历史、slots 槽位（目的地、天数、预算、偏好）、
plan_draft 行程草稿、tool_results 工具结果、revision_count 修订计数。六个节点：intake 槽位抽取
→ clarify 缺失反问 → plan 生成草稿 → tool_call 工具调用 → reflect 自检 → respond 流式输出。
• 条件边三处：槽位是否完整（不完整就反问，绝不让模型脑补）、自检是否通过、修订次数是否小于等
于 3
• reflect 检查预算超支、路线顺序、时间冲突，需要修订就回到 plan 节点
• 每个节点执行后状态都经 checkpointer 落 Redis，任意节点之间断线都能恢复
Q9｜Function Calling 怎么实现的？模型返回的参数不合法怎么办
核心答案 工具用 JSON Schema 定义——名称、描述、参数结构——随请求传给大模型的 tools 参数；
模型返回 tool_calls，服务端用 Pydantic 二次校验。校验失败的处理：把错误信息回喂给模型让它重新
生成，最多 2 次；仍失败就降级为默认值或向用户反问。
• 防参数幻觉：关键字段用枚举白名单（城市名、景点类别），必填字段非空校验
• 工具调用本身有 3 秒超时、1 次重试和熔断保护
• 工具返回值先压缩再回喂模型，只保留必要字段，省 token
Q10｜ReAct 和 Function Calling 有什么区别？你怎么选的
核心答案 ReAct 用 Prompt 模板驱动 Thought、Action、Observation 循环，是文本层面的推理；
Function Calling 是模型原生的结构化输出能力。我用同一组工具实现了两套并做了对照实验：FC 成功
率更高（约 98% 对 90%）、时延更低（省去文本解析）、token 更省（不用输出 Thought 文本）；
ReAct 的优势是可解释、不依赖模型的 FC 能力。所以 FC 为主线，ReAct 作为对照实验写进论文。
• 对比维度四个：成功率、平均时延、平均 token 消耗、可解释性
• 这个对照实验是现成的论文实验章节素材，答辩被问「你做过什么实验」时直接拿出来
Q11｜Reflection 自检是怎么做的？42% 的错误率下降怎么测的
核心答案 reflect 节点把行程草稿加槽位加工具事实一起交给模型，要求它按三个维度逐项自检：预算是
否超支、路线顺序是否合理、时间是否冲突；需要修订就回到 plan 节点，最多 3 次。测量方法：构建
50 条真实旅行请求的评测集，人工标注生成行程中的事实性错误——不存在的景点、错误的开放时间、
不合理的路线——错误率等于错误数除以检查点总数，对比开关自检的前后结果，相对下降 42%。
• 重点是讲清评测方法：评测集规模、标注标准、计算公式，方法比数字更有说服力
• 防过度反思：修订上限 3 次、单次执行全局步数上限、整体 120 秒超时，三重封顶
Q12｜记忆层怎么设计的？上下文长度怎么控制
核心答案 两层。短期记忆：Redis Hash 以 session_id 为键存对话历史和图状态，TTL 2 小时；上下文
组装用滑动窗口加摘要——最近 8 轮保留原文，更早的历史由小模型压缩成一段摘要。长期记忆：对话
中表达的稳定偏好回写 user_preferences 表，比如用户说过「不想爬山」，之后每次规划自动注入
system prompt。
