第一部分 项目总述与自我介绍
Q1｜请介绍一下这个项目
核心答案 这是一个对话式的智能旅行规划系统。用户用自然语言提出需求，比如「成都 4 天、预算
3000、带小孩」，Vue 3 前端收集需求并以 SSE 流式呈现规划过程；后端是 FastAPI 微服务集群，核心
的 agent-service 里用 LangGraph 编排状态图，驱动大模型通过 Function Calling 调用天气、景点、
路线工具，并结合 RAG 从攻略知识库检索背景知识，最终产出按天编排、可编辑保存的行程。工程上我
做了限流、熔断、幂等、分布式锁和 SSE 断开取消这些稳定性机制。几个关键数字：RAG 把行程信息准
确率从 71% 提升到 94%，自检修订让事实错误率下降 42%，缓存让高频接口响应缩短 61%。
• 讲述顺序：做什么 → 怎么做（技术主线）→ 工程亮点 → 量化结果，控制在 60 到 90 秒
• 数字是钩子，面试官大概率会追问，每个数字都要准备好测量方法的答案
• 结尾可以说「您对哪部分感兴趣我可以展开」，把主动权交回去
Q2｜这个项目和普通 CRUD 项目比，核心卖点是什么
核心答案 两点。第一是智能：它不只是存取数据，而是生成内容，有完整的 Agent 编排链路
——LangGraph 状态图、Function Calling、RAG、分层记忆。第二是工程性：大模型是「慢、贵、不
可靠」的下游，我围绕它建了一条完整防线——限流、熔断、幂等、分布式锁、SSE 生命周期管理，防
止模型或第三方异常引发雪崩。
• CRUD 是载体（用户、行程管理），Agent 是核心，稳定性是加分项，三者缺一不可
• 给一个具体细节比抽象概念更有说服力，例如：用户关掉页面后系统会自动取消大模型调用、停止计费
第二部分 总体架构与微服务
Q3｜为什么用微服务架构？毕业设计单体不够吗
核心答案 拆分的收益是故障隔离和独立伸缩。agent-service 是 IO 密集型，一次规划要等大模型几十秒
；trip-service 是纯 CRUD，毫秒级响应。混在一起，规划的慢调用会占满工作线程池，连行程列表查询
都被拖慢。但我也承认：微服务的真正红利在多人协作和独立发布阶段，所以毕业设计采取「逻辑微服
务、轻量部署」——代码按服务边界彻底分目录，每个服务独立容器，用 Docker Compose 在一台机
器上编排，架构完整且随时能演示。
• 拆成 5 个服务：网关（鉴权限流路由）、用户、行程、Agent、工具
• tool-service 独立的三个理由：工具被多场景复用、第三方限流缓存要统一治理、答辩时可一键切换
mock 数据源
• K8s 多集群写在论文展望里，坦承技术边界——这个坦诚本身就是加分项
