• 不压缩的后果：token 随轮次线性增长，既撑爆上下文上限又让费用失控
• 进阶选项：pgvector 存历史行程向量，语义检索相似行程作为规划参考
Q13｜断线恢复会话怎么实现？2 秒这个数字怎么来的
核心答案 checkpointer 在每个节点执行后把图状态写进 Redis。用户重新进入时，前端带 session_id
请求恢复接口，后端读出状态、重放最后一轮输出，不需要重新调用大模型。计时结果：恢复接口 P95
在 2 秒以内，瓶颈是 Redis 读取和前端渲染，而不是模型调用。
• 对比：没有 checkpointer 的话恢复等于重新规划一遍，几十秒且重复花钱
• 前端在 localStorage 缓存最后一份行程快照，先渲染再与后端同步，体感更快
Q14｜模型陷入死循环怎么办
核心答案 三层防线：第一，revision_count 封顶，反思修订最多 3 次；第二，单次图执行的全局步数上
限；第三，整体规划超时 120 秒，超时输出当前草稿并向用户说明。模型行为是概率性的，任何没有出
口的循环都会烧钱，封顶设计在生产里是必须的。
• 超时后的体验设计也要讲：不是报错，而是给出半成品加说明，用户可以选择继续
第四部分 RAG（切片 / 检索 / 幻觉治理）
Q15｜已经有 Function Calling 了，为什么还需要 RAG
核心答案 两者取的是不同性质的信息。Function Calling 取实时、结构化的事实——天气、路线、票价
；而攻略玩法、景点政策、避坑提示这类知识是非结构化、相对静态的，没有 API 可查，模型又特别容
易编造。RAG 从攻略语料库里检索出来注入 prompt，让模型「有据可依」。实时事实走工具，静态知
识走 RAG，这个互补是核心设计点。
• 举例说明：「某博物馆周一闭馆」这种信息没有实时 API，模型容易记错，RAG 检索最可靠
• 这个回答展示的是对信息性质的分类能力，而不是堆技术名词
Q16｜语料从哪来？怎么清洗的
核心答案 热门目的地攻略数十篇加景点官方介绍。清洗四步：去重、去掉导航栏广告和促销文案、标题
层级规范化、给每篇打城市标签作为元数据，供检索时过滤。
• 语料质量决定 RAG 的上限，垃圾进垃圾出
• 保留来源链接，前端展示引用时能溯源，也方便人工核对
Q17｜切片策略怎么定的？切大切小会有什么问题
核心答案 两级切片：先按结构切——标题、段落是天然边界；再限长——每块目标 300 到 500 token
，相邻块留 10% 到 15% 的重叠（约 50 token），防止句子被拦腰截断。切太小：语义不完整，检索命
中的是碎片，拼不出完整答案；切太大：噪声多，关键信息的相关性被稀释，还挤占上下文窗口。每个
块附元数据：城市、景点、来源。
