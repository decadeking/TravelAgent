• 事件类型六种：token 文本流、tool_call 和 tool_result 过程可视化、plan_update 行程更新、done、
error
• 工具调用过程卡片是交互亮点：用户能看到「查天气、搜景点、算路线」每一步，等 30 秒也不觉得卡
Q27｜用户断开连接后你做了什么
核心答案 清理链：取消规划任务 → 任务内部关闭大模型的 HTTP 流 → 写回会话状态 → 释放分布式锁
→ 连接注册表计数减一。用户离开的瞬间就停止计费。这是项目里印象最深的 bug：最初断开后任务还
在跑，日志里发现连接没了但 LLM 调用还在继续，才补上了完整的生命周期管理。
• 这个问题可以扩展成「最大困难」的答案：有现象、有排查、有方案、有反思
Q28｜前端怎么处理重连和重复内容
核心答案 fetch-event-source 的 onError 里按退避策略重试；重连后先 GET 会话状态恢复上下文，配
合幂等键防止重复发起规划；消息带事件编号，前端按编号去重，避免重复渲染。
• 幂等在这里闭环了：断线重连可能重发请求，request_id 保证大模型不会被重复调用
第六部分 稳定性设计（限流 / 熔断 / 幂等 / 分布式锁）
Q29｜限流怎么实现的？令牌桶和滑动窗口有什么区别
核心答案 双层。网关层用 Redis 加 Lua 的滑动窗口：zset 存请求时间戳，ZREMRANGEBYSCORE 清
理窗口外记录，ZCARD 计数，整段逻辑放 Lua 脚本保证原子性；单用户每分钟 10 次，全局 200 QPS
，超限返回 429 加 Retry-After。服务层用 asyncio.Semaphore 把大模型并发压到 20 以内。
• 令牌桶允许突发（桶容量决定突发上限），滑动窗口统计更平滑；对话场景要平滑，选滑动窗口
• 为什么双层：网关挡恶意刷量，服务层挡正常用户的并发洪峰
• 为什么用 Lua：多条 Redis 命令要原子执行，分开写会有竞态
Q30｜熔断怎么实现的？阈值多少？降级策略是什么
核心答案 每个下游独立一个熔断器实例——每个模型、每个工具各一个：10 秒统计窗口，失败率大于
等于 50% 且样本数大于等于 5 就打开，请求快速失败不再排队；30 秒冷却后进入半开，放行 3 个探测
请求，全部成功才关闭。降级分层：大模型不可用，返回缓存的热门行程模板加规则化推荐，页面明示
「智能规划维护中」；天气工具不可用，行程标注「暂无天气数据」，不阻塞主流程。
• 降级是「系统仍有答案」，不是假装无事发生，前端必须明示降级状态
• 样本数门槛防止单个请求失败就误判熔断
