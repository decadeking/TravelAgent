• 重叠的作用：边界信息不丢，比如「开放时间早八点」正好跨在两块之间
• 块大小不是拍脑袋：用评测集观察 recall@5 随块大小的变化来调
• 切片问题的标准答法是「策略加理由加调优方法」三段式
Q18｜Embedding 模型怎么选
核心答案 三个标准：中文效果（看 C-MTEB 榜单）、维度与检索成本、部署方式（本地还是 API）。语
料是中文攻略，所以选中文优化的向量模型；查询和语料必须用同一个模型编码，保证在同一向量空间
里比较。
• 维度权衡：维度越高表达力越强，但存储和相似度计算成本也越高
• 部分模型对 query 和 document 支持不同的指令前缀，用对前缀能明显提升检索效果
Q19｜为什么用 pgvector？和 Chroma、Milvus 什么区别？HNSW 了解吗
核心答案 业务数据在 MySQL，向量检索单独用一个 PostgreSQL 加 pgvector 实例。选它的理由：
SQL 生态熟悉、支持元数据过滤（先按城市过滤再向量检索）、百万级数据量下 HNSW 索引的召回和
时延都够用。Chroma 轻量适合原型，生产运维和过滤能力弱；Milvus 功能强但运维重，毕业设计的数
据量用不上。索引选 HNSW 而不是 IVFFlat：召回更高、支持增量写入、不需要预训练聚类中心。
• HNSW 参数：m=16、ef_construction=64，ef_search 按召回和时延的平衡调
• HNSW 原理：多层跳表式图结构，上层稀疏快速定位区域，下层稠密精确搜索，查询复杂度约 O(log N)
Q20｜检索 top-k 怎么定？检索不准怎么办
核心答案 top-k 取 5，两级过滤：先按城市元数据过滤，再按相似度阈值（余弦大于等于 0.5）剔除不相
关块。精度不够时加一层重排：用 cross-encoder 重排模型对 top-20 候选精排——它把查询和文档拼
在一起打分，比双塔相似度更准，但慢，所以只用于精排少量候选。
• 建 badcase 集调检索：记录「查询到期望命中的块」，观察 recall@5，针对性优化
• 查询改写：用小模型把口语化查询改写成检索友好形式，比如「带娃去哪好玩」改成「适合亲子游的景
点」
• 强调调检索是迭代过程，体现工程经验而不是调参玄学
Q21｜检索结果怎么注入 Prompt？会不会挤占上下文
核心答案 把 top-k 块拼成「参考资料」块放在规划请求里，并附明确约束：优先依据资料回答，资料没
有的用工具结果，都没有就明确说不知道。总量控制在 2000 token 以内，超了按相似度从高到低截断。
保留块编号，前端展示引用来源。
• 资料块放在 user 消息里，与 system prompt 隔离，这本身也是 prompt 防护的一部分
• 明确允许模型说「不知道」，是降低幻觉的关键指令——不给它编造的压力
