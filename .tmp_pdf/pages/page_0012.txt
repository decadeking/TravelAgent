Q35｜表结构怎么设计的？为什么拆成三级
核心答案 行程三级结构：trips 主表存元数据——目的地、天数、预算、状态、版本；trip_days 按天拆
分——城市、天气快照；itinerary_items 存具体安排——景点、顺序、时间、费用。拆分收益：单天操
作（增删一天）不动全表，前端可按需加载，查详情只取需要的天。
• 另有 users、user_preferences（记忆回写）、agent_sessions（会话状态）、llm_call_logs（调用台账）
• 反范式权衡：行程项冗余 poi_name，列表展示时免连表
Q36｜建了哪些索引？54% 的提升怎么测的
核心答案 为高频查询路径建索引：trips 建 (user_id, updated_at DESC) 支撑行程列表排序；trip_days
建 (trip_id, day_no) 唯一约束；itinerary_items 建 (day_id, seq) 顺序读取当日行程；llm_call_logs 两
个索引分别支撑成本统计和链路排查。测量：慢查询日志加 EXPLAIN——加索引前列表查询是全表扫描
type=ALL，加索引后 type=ref，实测 SQL 平均耗时下降 54%。
• 索引不是越多越好，每个索引都有写入代价，只为高频路径建
• 现场可讲 EXPLAIN：访问类型、扫描行数、Extra 里的 Using index 表示覆盖索引
• 最左前缀原则：(user_id, updated_at) 索引在只查 updated_at 时不生效
Q37｜事务怎么用的？为什么选先删后插
核心答案 行程保存是强一致场景：trips、trip_days、itinerary_items 在同一数据库事务里写入，要么
全部成功要么整体回滚。更新策略用先删后插的全量替换：Agent 每次生成的是完整行程，diff 更新逻
辑复杂易错，先删后插简单可靠，数据量小（单行程几十行）性能无压力。
• 并发修改靠乐观锁兜底：更新时 WHERE 带 version，不匹配提示用户刷新
• 为什么不用悲观锁：行程编辑是低争用场景，乐观锁不占数据库锁，并发性能更好
Q38｜缓存一致性怎么保证？穿透、击穿、雪崩怎么处理
核心答案 cache-aside：先读缓存，未命中读库回填并设 TTL；写的时候先更新数据库再删缓存——是
删而不是更新，因为并发写时更新缓存可能出现旧值覆盖新值。穿透（查不存在的数据）：缓存空值加
短 TTL，加参数校验；击穿（热点 key 过期）：互斥重建，只放一个请求回源；雪崩（大量 key 同时过
期）：TTL 加随机抖动。
• 不同数据的一致性要求不同：天气缓存允许最多 1 小时不一致，会话缓存 TTL 2 小时
• 这三连问是缓存必考题，按「一致性方案加三个异常场景」的结构完整作答
Q39｜61% 的响应时间缩短是怎么测的
核心答案 会话历史查询是高频接口——每次打开对话页都会调用。之前每次从 MySQL 读 state_json 再
反序列化，之后直接读 Redis Hash。用 locust 在 100 并发下压测，对比前后平均响应时间，缩短 61%。
• 压测条件要能复述：并发数、持续时间、机器环境，数字必须可复现
• 缓存命中率也接进了 Prometheus 监控，命中率骤降说明有问题
